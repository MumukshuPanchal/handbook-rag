# ADR 0016: A demo page without a build step

- Status: Accepted
- Date: 2026-11-23

## Context

[Issue 19](https://github.com/MumukshuPanchal/handbook-rag/issues/19) asks for a page where someone types a question and watches the cited answer arrive. The API already sends the answer as server-sent events while the model writes ([ADR 0015](0015-answers-over-http.md)), so the page only has to ask and show.

Four facts shaped it:

- **The answer is written by a model from pages that anyone at the company can edit.** In the adversarial tests a passage that asked for a made-up link at the end of every answer got it three times in four, under an answer that was right ([the evaluation guide](../evaluation.md#adversarial-tests)). What the model writes is therefore untrusted text, and a page that showed it as HTML or turned its addresses into links would hand that link to the reader. Making the model resist is [issue 66](https://github.com/MumukshuPanchal/handbook-rag/issues/66), and is not done.
- **`POST /ask` is a POST with a JSON body.** The browser's own reader of server-sent events, `EventSource`, only sends a GET request without a body.
- **The project has no JavaScript toolchain**: no package manager, no bundler, no test runner for a browser. Everything else is Python, checked by ruff, mypy and pytest.
- **The service has no login.** It listens on this machine only unless told otherwise, and every answer spends the key's allowance of 15 requests a minute and 500 a day ([ADR 0015](0015-answers-over-http.md), [ADR 0014](0014-answer-evaluation-in-stages.md)).

## Decision

1. **Three files written by hand, served by the API itself.** `GET /` serves the page, `GET /static/demo.js` its script and `GET /static/demo.css` its style. They live in the package, in `src/handbook_rag/static/`, are found through `importlib.resources`, and travel in the wheel, which is how the container image installs the project. CI checks that the image holds them. They are read once, when the application is built, so a file missing from the package stops the service from starting instead of failing at the first page load.
   - No framework, no build step, no package manager, and nothing loaded from another site: no CDN, no web font. What the browser runs is what is in the repository, there is no toolchain to keep up to date, and a reader can read all of it.
   - `HANDBOOK_RAG_API_DEMO`, true by default, switches the page off: the three addresses then answer 404. They take GET only, and are left out of the API's documentation. No request to them is traced, whatever its method, and also while the page is switched off, as for `/health`: a page load is not a question. A question asked on the page is a request to `/ask`, traced like any other.
2. **`fetch` with a stream reader, not `EventSource`.** The page sends `POST /ask` with `"stream": true` and reads the response body as it arrives. It parses the events itself, in a few small functions: a piece of the stream can end inside an event or hold several, a character's bytes can be split between two pieces, and a line may end in `\r\n`, `\n` or `\r`, as the standard allows, even with a `\r` at the end of one piece and its `\n` at the start of the next. The service sends `\n`; something between it and the browser may not. A reply that is not an event stream at all is reported by what it was. The same request can be stopped: the page's stop button aborts it, and the service then stops the model at its next piece of text, as for any caller who goes away.
3. **Everything from the API is shown as text.** The script builds each element and sets its `textContent`. It uses no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `Function` or inline event handler, and nothing that takes the reader to another page, such as `location` or `window.open`: it has no reason to. A test reads the whole script, its comments included, and fails if one of these names appears in it. What gets past that test is listed under "What is not tested".
   - **Nothing in an answer becomes a link.** An address in the answer's text stays text. The only links are the sources' pages, made in one function of the script from the `url` field, and only for an address that starts with `https://` or `http://`. That address is built by the indexer from the handbook's address and the page's path, not taken from the page's text. The page's title, which whoever edits the page writes, is the link's text, so the address is also written out under it, and the reader sees where the link leads before following it. A link opens in a new tab, with `rel="noopener noreferrer"`. The passages' text is shown as text too.
4. **No Markdown rendering.** The model writes Markdown, and the passages hold it. Turning it into HTML would need a parser in the page and a sanitiser after it, and a mistake in either would undo point 3. The cost is seen at once: bullets, bold and headings show as the model typed them, with their asterisks and hashes. Line breaks are kept.
5. **A strict content security policy**, sent as a header with the page and its two files: `default-src 'none'`, then `'self'` for the script, the style and the requests to the API, and nothing else. So no inline script or style runs, nothing comes from another origin, no other page can frame this one (`frame-ancestors 'none'`), and no form sends anywhere (`form-action 'none'`). `require-trusted-types-for 'script'` with `trusted-types 'none'` makes a browser that supports Trusted Types refuse any HTML written from a string, as a second line behind point 3. Each file also carries its content type with a charset, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-cache`, which lets the browser keep a copy but not use it without asking the server. No `ETag` or `Last-Modified` is sent, so there is nothing to check a copy against, and every load fetches the three small files again. A changed file reaches the reader at the next load.
6. **For this machine only.** The page adds no login and no limit. It is meant for whoever runs the service, at <http://127.0.0.1:8000/>, and the page says that every question asked on it spends the key's allowance.

What the page shows: the text as it arrives; then the answer built from its segments, with the numbers of each segment's sources as small buttons after it that bring the source into view; the sources with their number, title, the address of their page written out, headings, a link to the page and the passage folded away; the model, the tokens read and written, the time to the first text and to the whole answer, why the model stopped, and the trace id with a button that copies it. (Note, 2026-11-23: when an answer took more than one request, or the fallback model wrote it, the page also shows how many requests it took and which model gave the answer, [ADR 0018](0018-time-limits-retries-and-a-fallback.md). A service that does not send those fields is shown as before.) A field that is missing shows as "unknown". A reply that is not an answer is shown as such, set apart from an answer. Every failure is put in words: a 503 with the service's own words and, when a `Retry-After` header came, how long to wait; a 422; an `error` event in the middle of an answer; a network failure; a stream that ends without its answer; a reply that is not a stream; and an answer the page cannot read. Beside the answer, folded away, are the passages `POST /search` returns for the same question, so that what was found can be compared with what was cited, without a request to the model. It follows the reader's light or dark setting.

It is built for a keyboard and a screen reader: real labels, a visible focus, and Ctrl+Enter, or Cmd+Enter on a Mac, to ask without leaving the question box, where Enter starts a new line, as the hint under the box says.

- **What a screen reader user hears.** The status line is a polite live region, and it says each state of the request: that it is asking, that the model is writing, that the answer is complete and how many sources it cites, that the reply is not an answer, or that the answer was stopped. A failure is read at once, from an alert region. A message said twice, such as copying the trace id twice, is announced both times. The streamed text itself is not announced: it arrives in pieces, and each piece would be read on its own. When the status line says that the answer is complete, the reader moves to it, under the heading "Answer". Each source's folded passage is named for its source. How all this sounds in a real screen reader has not been tried.
- **A number button does not move the focus.** It brings its source into view and marks it, and the status line says which source is marked and where. Moving the focus to the source would need a way back to the place in the answer: one more control on every source, and more to check by hand. Leaving the focus on the button is the simpler of the two. The reader stays where they were, can press the next number, and reaches the sources by moving on through the page.

### Note, 2026-11-25: a conversation instead of a form

The page is the first thing a visitor sees of the project, and it looked like a form. Its look and its structure were changed. Its guards hold as before, with one change in how the page says what it sends, given below; a review of the change found two of them weaker and one test looser than this note claimed, and they were fixed before the merge.

- **What changed in its structure.** The page holds turns: each question is a bubble, and its answer is a card under it, which the script builds for each turn, so the line about the question searched for, the streamed text and the failure belong to their turn and are no longer elements of the page's markup. The question box is docked under the conversation. The sources are cards beside the answer on a wide screen and under it on a phone: their number, the page's title as the link followed by the headings above the passage, a piece of the passage without its Markdown headings (cut as text, nothing rendered), the page's address in brief (the host and the path as a breadcrumb, its middle left out when it runs long, on a line that wraps), and the whole passage folded away. Pointing at or focusing a number marks its card, and pointing at or focusing into a card marks the numbers that cite it; pressing a number still marks the card, brings it into view and leaves the focus where it was. Under each answer, a strip of labelled badges sums up how it was made: how many passages the search found (from the search the page runs beside the answer, because the answer does not carry that number), how many sources it cites, what the rewriting step did, whether it came from the cache and from which tier, the model, the times and the tokens; every fact the page showed before is still shown, under "All details". A decline (`answered` false and a normal end, `end_turn` or `no_context`) is a calm notice, and a reply withheld or cut off is a notice of its own that names why the model stopped; a failure is a card that says what happened and offers to ask again; placeholders stand for the text and the sources until they come, and a caret ends the text while it is written. Each turn has its own fold of the passages the search found; when a follow-up's answer came without saying which question was searched for, no search ran, and the badge says "not run". "Start a new conversation" also takes the turns off the page, and a fold above the box lists the questions that will be sent; the fold scrolls within a fixed height, so that its own control stays on the screen. The "Cited" badge and the status line count the sources the answer's text cites, which can be fewer than those it lists. A source whose card cannot be built stands as a card that says so, under the source's number, so that pressing the number still brings it into view, and the answer and the other cards are shown; a found passage that cannot be built stands in the same way: building the answer still cannot fail halfway. The word over each card says how its turn ended: "Answer", "Declined", "Reply" for one withheld or cut off, "Failed" or "Stopped", and the strip under a reply that is not an answer is named for a reply. The stop button shows only while an answer is being written, beside Ask, which shows a turning ring then; if the stop button held the focus when it goes, the focus goes back to the question box. On a phone the two controls above the box share one row, the status line is cut to one line on screen beside the count and read out whole, and the steps of "What happens when you ask" (the search first, then the answer, the decline, the rewritten follow-up and the stored answer) are folded away, closed: the same steps, held to the same words by a test, are a card beside the welcome on a larger screen. The header leads to the README's sections on how the system works and how it is measured, in a new tab. A fourth example question is one the handbook does not answer, marked as such on the page, so that a visitor sees a decline on purpose.
- **What changed in its look.** A type scale and a spacing rhythm, one accent colour, light and dark themes that follow the system's setting, cards with a soft shadow, visible focus rings, and small motion (a turn rising in, the caret, the placeholders' shimmer) that is switched off under `prefers-reduced-motion`. Every pair of text and background meets WCAG AA in both themes, and the question box's edge stands out by 3:1. The system's fonts only. The icons are shapes drawn in the style sheet or inline SVG in the page's markup: no image, no icon font, and no `data:` address, which `default-src 'none'` refuses anyway.
- **Enter asks; Shift+Enter starts a new line.** Until now Enter started a new line and only Ctrl+Enter or Cmd+Enter asked: a visitor who tries a chat box types and presses Enter, and nothing happened. Enter now asks, and Ctrl+Enter and Cmd+Enter still do. Enter asks nothing while a character is being composed with an input method (`isComposing`, and the key code 229 that Safari sends with the Enter that ends a composition), nor with an empty box, nor with a question over the limit, nor while an answer is being written; the hint under the box says which keys do what.
- **Where a source's link leads, still seen, in less room.** The card shows the address in brief: the host, then the path, whose middle parts are left out when it runs long; only a last part that is long by itself is cut, in its middle. The host is never cut, since it says which site the link leads to: it is the host the browser reads, so a name before an `@` is not taken for it, and a host in another script shows in punycode. The line wraps, on the sources and on the found passages, and a test reads every rule of the style sheet, inside media queries and with `!important` too, and fails on the ways of hiding or cutting text it knows of (an ellipsis, a clamp, a height limit, a `white-space` that does not wrap, `overflow` or `contain` that clips, `display: none`, `visibility: hidden`, a clip, zero opacity or size, a transparent colour), set on the line, on an element or attribute selector that could reach it, or on the card, the found passage or any element around them, where an inherited `white-space` counts too. It does not compute the cascade, and it does not know every way a style sheet can hide text: one it does not list gets past it. (The first version cut the line with an ellipsis, which could hide part of a long host; the review found it.) The whole address stays within reach: it is the link's title, shown when the link is pointed at; it is written out at the top of the fold with the passage; and it is what a screen reader reads, in place of the brief one. The link itself is made as before, in `sourceLink` alone, from the checked address.
- **What changed in how the page says what it sends.** The old page showed its whole notice whenever there was a conversation. Its words are now in the fold above the box, with the list of questions, and one short line under the fold says, whenever there is a conversation, that only questions are sent, never answers, and that they are kept on this page only.
- **What did not change.** The content security policy, word for word; no inline script or style; only the page's own two files; everything from the API set as text; links made in `sourceLink` alone, for `https://` and `http://` addresses; nothing kept in the browser; the status line and the alert region as the only announcing regions (the alert region is now read and not shown, and the failure card in the turn shows the same words); a stop is announced in the status line; the conversation that is sent.
- **The tests, changed to hold the same rules on the new structure.** The test of the keys now asks that the hint name Enter and Shift+Enter, that the box declare the keys that ask, and that the script's test of a key look at Shift and at a composition; what each key does is run in node. The markup test asks that the stop button be hidden before the script runs, and that the two copies of the steps be the same. The test of the one link maker also asks that the whole address be the link's title. The markup test now names the page's own links exactly, the two to the README with `rel="noopener noreferrer"` and `/docs`, and refuses the parts of an inline SVG that could fetch a file (`use`, `image`, `feImage`, `foreignObject`, an `href` on anything but a link). The example questions must each be a golden question of the type they show, with exactly one unanswerable one, which the page labels. The check that the streamed text is not announced now asks that the script makes no live region at all: no `aria-live` as an attribute or as the property `ariaLive`, no role, and no `output` element. The rules on markup bound the HTML only, and the script builds most of the page, so it is now held to a fixed list of the elements it may make, each named in a string (none that loads, runs or announces anything), and may never set `src`, `srcset` or `style`, by name or in brackets. A test of the style sheet does what is said above for the address line, within the limits said there, and another holds the notice of what is sent and its controls to being seen and heard: no `hidden` or `aria-hidden` on the notice or its area in the markup, no rule that hides them, a height limit on the fold, the words a phone does not show still read out, and the new-conversation button on one line. The words that a cached answer ran no search, and the searched-for line made hidden with each turn, are checked in the script, where they now are. The test that runs the script in node has a fuller fake page, with nested elements, classes, the hidden flag and events, and reads back what a reader would see. Beside the conversation it ran before, it checks the bubbles, the notices and failure cards, the placeholders and the caret while an answer comes, the stop button, the badges, the source cards with their link, headings, piece of text and address, and the marking of numbers and cards, the address in brief beside the whole one, the keys (Enter, Ctrl+Enter and Cmd+Enter ask; Shift+Enter, an Enter during a composition, an empty box, a question over the limit and an Enter while an answer is being written do not), the stop button shown only while an answer is being written, and the word over each card. After the review it also wires the example buttons, tracks the focus, has a clipboard and searches that find one passage, fail or are refused, and checks "Ask again", the copy of a trace id, the found passages with their links and addresses, the new-conversation button and the alert after a new conversation, the count of what is sent past ten questions, the announcements of a decline and of a withheld reply, the warning badges, the words each control speaks, and the address in brief for an address with no path, a very long host, a name before the host, a host in punycode and a port. 112 planted faults, the review's 40 among them, are each found by the run, and a card made to fail leaves the answer shown.
- **What is not tested.** The look itself: it was checked by eye in Chromium, on a stand-in service that served the page with this code and answered with replies of the API's shape, most of them real replies saved on 25 November 2026, at 1280 by 800 and 390 by 844 pixels, light and dark. Not tried: another browser, a screen reader, a keyboard alone through a whole conversation, and a real service.

## Alternatives considered

- **A front-end framework**, such as React, Vue or Svelte. It would bring a package manager, a build step and a lock file of its own to keep up to date, for one page with one form. It would also make it harder to see that nothing writes HTML: a framework escapes text by default, but each has a way around it.
- **A Markdown library in the page**, to render bullets and bold. Each one turns text into HTML, which is the thing point 3 rules out, and needs a sanitiser after it. Showing the asterisks is the smaller cost.
- **A separate front-end project**, in its own folder or repository, deployed on its own. Two things to run and to version instead of one, and a second origin, which would need cross-origin rules on the API.
- **A public deployment.** The service has no login and no limit for each caller, and its key is a free one, so anyone who found the page could spend the day's allowance ([ADR 0015](0015-answers-over-http.md), "What is still missing").

## What is not tested

- **The script, in a browser, by an automated test.** The project has no JavaScript toolchain, and adding one for this page would cost more than the page. The tests check what can be checked without a browser: the status, content type and headers of each file, that the setting switches them off, that they take GET only, that they are not in the API's documentation, that no request to them leaves a trace whatever its method and also while they are switched off, the policy, that the markup has no inline script or style and loads only its two files, that the example questions are real test questions, that every element the script looks up is on the page, that the hint names the keys that ask and the script listens for them, and that the script holds none of the forbidden names and makes links in one function only. How the page behaves (the events read from a real stream, the answer built from its segments, each failure shown, the stop button, the keyboard and the screen reader) is left to a check by hand, in a real browser against the real service.
- **What the check by hand covered, on 23 November 2026**, in a real browser against the real service, on an evening when the answer model was overloaded: an answer that cited three sources, with its number buttons marking their source, the passages folding open, and the links opening the handbook's pages with `noopener noreferrer`; a question outside the handbook, shown as a decline; the stop button, pressed while the model had not yet written; and a reply that the provider broke off halfway with a "high demand" error, where the page kept what had arrived and said that it was incomplete. The browser's console showed no error and no warning from the policy. One slip was seen and fixed: a style rule for the search panel's heading also enlarged the headings of the passages folded inside it. Not tried by hand: a keyboard alone, a screen reader, the dark colours, a 422, a 503 with `Retry-After`, and a browser other than Chromium. The fixes made after a review later that day came after this check. A second check by hand followed them, this time against the Docker Compose stack, which is what issue 19 asks for: the image was built with the page inside it, the API container was started with `docker compose up`, and the page was opened from that container. It answered a question asked with Ctrl+Enter, with one cited source whose address stood as text under its title; its number button marked the source, said so in the status line and left the focus in the question box; the fold was named for its source; the status line and the alert were the page's only announcing regions; and the console was again empty. Still not tried in a browser, besides what the first check left out (a keyboard alone, a screen reader, the dark colours, a 422, a 503 with `Retry-After`, a browser other than Chromium): the other line endings of the stream, a reply that is not a stream, an answer of the wrong shape, "unknown" for a missing field, the words for a wait of 0 seconds or of hours, and a repeated message announced again. Their pure functions were run once in Node, outside the project, and are not tested.
- **The check of the script reads its source, not what it does.** It reads the whole file, comments and strings included, and fails if a forbidden name appears anywhere in it: the ways to read a string as markup (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `write`, `DOMParser` and its kin), to run a string as code (`eval`, `Function`, `constructor`, `setTimeout`, `setInterval`, an inline event handler), and to take the reader to another page (`location`, `open`, `history`, the Navigation API, a refresh by a meta element). The newer `setHTML` is among the first group, and making an attribute as a node of its own is forbidden too, since that is a way to give an element an address without writing the word. It also fails if an address is set, or a link element is made under its name in either letter case, outside `sourceLink`. What still gets past it is a name it cannot see: one built from pieces, such as `el["inner" + "HTML"]` or `link["hr" + "ef"]`, or one reached through a variable or through another object. Of the ways round it that the second review of the redesigned page named, the check now sees `make` kept under another name or called through `call` or `apply`, `Object.assign`, a style map (`attributeStyleMap`) and a style sheet written by the script (`insertRule`, `styleSheets`, `adoptedStyleSheets`). It does not see a class name, or `classList`, given text from the API (today every class name comes from the script's own words), nor names built from pieces, nor the `hidden` flag set on a line that must show: the node test checks that the address under every source and found passage is shown, and the markup and the style sheet are checked for the notice of what is sent, but no other line. The list of names is what two rounds of review thought of. It is not complete, and a new browser interface can add to what it misses. For each kind, what else stands in the way:
  - **Loading or running code.** The policy stops it in every browser that enforces a content security policy, whatever the script does. `script-src 'self'`, without `'unsafe-inline'` or `'unsafe-eval'`, refuses inline script, event handlers written as attributes and code made from strings. `connect-src 'self'` keeps the page's requests on this server. `default-src 'none'` refuses everything else, such as images, frames and fonts.
  - **Markup written from a string.** Trusted Types make the browser refuse it, but only a browser that supports them, such as one built on Chromium. In another browser the markup would be parsed. A script in it would still be stopped by the policy, but markup that runs no code, such as a link planted in a page, would show on the page, and nothing but the check stands against that.
  - **Taking the reader to another page, or showing a link that runs no code.** Nothing but the check. A link made under a name the check cannot see, with an address set the same way, would show on the page in any browser. The policy governs what the page loads and where its forms send, not where the page itself goes.

## Consequences

- Anyone who runs the service can show it working without a terminal, and see in one place the answer, what it cites and what the search found.
- The service now has one more surface: three addresses that serve files. They read no input, and the policy limits what the page can do even if a later change to the script went wrong.
- An answer's formatting shows as the model typed it.
- A change to the page is a change to three files that a reader can open and read; no build output is committed or served.
