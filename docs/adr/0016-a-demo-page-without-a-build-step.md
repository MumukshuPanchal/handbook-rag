# ADR 0016: A demo page without a build step

- Status: Accepted
- Date: 2026-11-23

## Context

[Issue 19](https://github.com/MumukshuPanchal/handbook-rag/issues/19) asks for a page where someone types a question and watches the cited answer arrive. The API already sends the answer as server-sent events while the model writes ([ADR 0015](0015-answers-over-http.md)), so the page only has to ask and show.

Four facts shaped it:

- **The answer is written by a model from pages that anyone at the company can edit.** In the adversarial tests a passage that asked for a made-up link at the end of every answer got it three times in four, under an answer that was right ([the evaluation guide](../evaluation.md#adversarial-tests)). What the model writes is therefore untrusted text, and a page that showed it as HTML or turned its addresses into links would hand that link to the reader. Making the model resist is [issue 66](https://github.com/MumukshuPanchal/handbook-rag/issues/66), and is not done.
- **`POST /ask` is a POST with a JSON body.** The browser's own reader of server-sent events, `EventSource`, only sends a GET request without a body.
- **The project has no JavaScript toolchain**: no package manager, no bundler, no test runner for a browser. Everything else is Python, checked by ruff, mypy and pytest.
- **The service has no login.** It listens on this machine only unless told otherwise, and every answer spends the key's allowance of 15 requests a minute and 500 a day ([ADR 0015](0015-answers-over-http.md), [ADR 0014](0014-answer-evaluation-in-stages.md)).

## Decision

1. **Three files written by hand, served by the API itself.** `GET /` serves the page, `GET /static/demo.js` its script and `GET /static/demo.css` its style. They live in the package, in `src/handbook_rag/static/`, are found through `importlib.resources`, and travel in the wheel, which is how the container image installs the project. CI checks that the image holds them. They are read once, when the application is built, so a file missing from the package stops the service from starting instead of failing at the first page load.
   - No framework, no build step, no package manager, and nothing loaded from another site: no CDN, no web font. What the browser runs is what is in the repository, there is no toolchain to keep up to date, and a reader can read all of it.
   - `HANDBOOK_RAG_API_DEMO`, true by default, switches the page off: the three addresses then answer 404. They are left out of the API's documentation, and their requests are not traced, like those to `/health`: a page load is not a question. A question asked on the page is a request to `/ask`, traced like any other.
2. **`fetch` with a stream reader, not `EventSource`.** The page sends `POST /ask` with `"stream": true` and reads the response body as it arrives. It parses the events itself, in a few small functions: a piece of the stream can end inside an event or hold several, and a character's bytes can be split between two pieces. The same request can be stopped: the page's stop button aborts it, and the service then stops the model at its next piece of text, as for any caller who goes away.
3. **Everything from the API is shown as text.** The script builds each element and sets its `textContent`. It uses no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function` or inline event handler. A test reads the script and fails if one appears.
   - **Nothing in an answer becomes a link.** An address in the answer's text stays text. The only links are the sources' pages, made in one function of the script from the `url` field, and only for an address that starts with `https://` or `http://`. That address is built by the indexer from the handbook's address and the page's path, not taken from the page's text. A link opens in a new tab, with `rel="noopener noreferrer"`. The passages' text is shown as text too.
4. **No Markdown rendering.** The model writes Markdown, and the passages hold it. Turning it into HTML would need a parser in the page and a sanitiser after it, and a mistake in either would undo point 3. The cost is seen at once: bullets, bold and headings show as the model typed them, with their asterisks and hashes. Line breaks are kept.
5. **A strict content security policy**, sent as a header with the page and its two files: `default-src 'none'`, then `'self'` for the script, the style and the requests to the API, and nothing else. So no inline script or style runs, nothing comes from another origin, no other page can frame this one (`frame-ancestors 'none'`), and no form sends anywhere (`form-action 'none'`). `require-trusted-types-for 'script'` with `trusted-types 'none'` makes a browser that supports Trusted Types refuse any HTML written from a string, as a second line behind point 3. Each file also carries its content type with a charset, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-cache`, so the browser checks with the server before it uses a copy and a changed file reaches the reader.
6. **For this machine only.** The page adds no login and no limit. It is meant for whoever runs the service, at <http://127.0.0.1:8000/>, and the page says that every question asked on it spends the key's allowance.

What the page shows: the text as it arrives, in a polite live region; then the answer built from its segments, with the numbers of each segment's sources as small buttons after it that bring the source into view; the sources with their number, title, headings, a link to the page and the passage folded away; the model, the tokens read and written, the time to the first text and to the whole answer, why the model stopped, and the trace id with a button that copies it. A reply that is not an answer is shown as such, set apart from an answer. Every failure is put in words: a 503 with the service's own words and, when a `Retry-After` header came, how long to wait; a 422; an `error` event in the middle of an answer; a network failure; and a stream that ends without its answer. Beside the answer, folded away, are the passages `POST /search` returns for the same question, so that what was found can be compared with what was cited, without a request to the model. It is built for a keyboard and a screen reader: real labels, a visible focus, the streaming text in a polite live region and the state of the request announced. How it sounds in a screen reader has not been tried. It follows the reader's light or dark setting.

## Alternatives considered

- **A front-end framework**, such as React, Vue or Svelte. It would bring a package manager, a build step and a lock file of its own to keep up to date, for one page with one form. It would also make it harder to see that nothing writes HTML: a framework escapes text by default, but each has a way around it.
- **A Markdown library in the page**, to render bullets and bold. Each one turns text into HTML, which is the thing point 3 rules out, and needs a sanitiser after it. Showing the asterisks is the smaller cost.
- **A separate front-end project**, in its own folder or repository, deployed on its own. Two things to run and to version instead of one, and a second origin, which would need cross-origin rules on the API.
- **A public deployment.** The service has no login and no limit for each caller, and its key is a free one, so anyone who found the page could spend the day's allowance ([ADR 0015](0015-answers-over-http.md), "What is still missing").

## What is not tested

- **The script, in a browser, by an automated test.** The project has no JavaScript toolchain, and adding one for this page would cost more than the page. The tests check what can be checked without a browser: the status, content type and headers of each file, that the setting switches them off, that they are not in the API's documentation and leave no trace, the policy, that the markup has no inline script or style and loads only its two files, that the example questions are real test questions, that every element the script looks up is on the page, and that the script holds none of the forbidden calls and makes links in one function only. How the page behaves (the events read from a real stream, the answer built from its segments, each failure shown, the stop button, the keyboard and the screen reader) is left to a check by hand, in a real browser against the real service.
- **What the check by hand covered, on 23 November 2026**, in a real browser against the real service, on an evening when the answer model was overloaded: an answer that cited three sources, with its number buttons marking their source, the passages folding open, and the links opening the handbook's pages with `noopener noreferrer`; a question outside the handbook, shown as a decline; the stop button, pressed while the model had not yet written; and a reply that the provider broke off halfway with a "high demand" error, where the page kept what had arrived and said that it was incomplete. The browser's console showed no error and no warning from the policy. One slip was seen and fixed: a style rule for the search panel's heading also enlarged the headings of the passages folded inside it. Not tried by hand: a keyboard alone, a screen reader, the dark colours, a 422, a 503 with `Retry-After`, and a browser other than Chromium.
- **The check of the script reads its source, not what it does.** It looks for the forbidden calls by name, and skips comment lines. A call reached by another name, such as a property read through a variable, would get past it.

## Consequences

- Anyone who runs the service can show it working without a terminal, and see in one place the answer, what it cites and what the search found.
- The service now has one more surface: three addresses that serve files. They read no input, and the policy limits what the page can do even if a later change to the script went wrong.
- An answer's formatting shows as the model typed it.
- A change to the page is a change to three files that a reader can open and read; no build output is committed or served.
