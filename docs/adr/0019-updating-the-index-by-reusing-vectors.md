# ADR 0019: Updating the index to a newer commit by reusing vectors

- Status: Accepted
- Date: 2026-11-23

## Context

The handbook is indexed at one pinned commit ([ADR 0002](0002-handbook-corpus.md)). A collection's name holds the first eight characters of that commit, the two models and the chunking version, so vectors made under different settings are never mixed in one index ([ADR 0004](0004-qdrant-as-vector-store.md)). [Issue 21](https://github.com/MumukshuPanchal/handbook-rag/issues/21) asks for the index to follow the handbook without embedding everything again.

Two facts made that impossible before this change:

- **Indexing was safe to repeat only inside one collection.** A chunk whose id was already stored was skipped, and stored chunks no longer produced were removed. A newer commit has a collection of its own, which starts empty, so all 38,881 chunks were embedded again. On a CPU that takes 45 to 56 minutes ([ADR 0012](0012-retrieval-gate-on-a-slice.md)), although only a small part of a handbook changes from one day to the next.
- **The id is not what a vector is made from.** A chunk's id is made from the page's path, the chunk's position, the chunking version and the chunk's text. What is embedded is the page's title and the headings above the chunk, then the chunk's text (`Chunk.text_for_embedding`). What is stored beside the vectors also holds the address, the section and the commit. So a chunk can keep its id while what should be embedded and stored for it changes.

The second fact was a hole in the skipping as well, and it could be reached inside one collection, without a new commit. Within one commit the handbook's text cannot change, but two other things can change while ids and the collection's name stay the same: a setting (`HANDBOOK_RAG_HANDBOOK_BASE_URL` changes every chunk's address), and the code (a change to how titles are read from the front matter, or to how heading names are cleaned, changes titles and headings without changing any chunk's text). In both cases `index` skipped every chunk and kept what it had stored before.

## Decision

1. **Each commit keeps a collection of its own.** The newer commit is indexed into a new collection beside the older one, as before. The older collection is only read, so it stays exactly as it was until the setting is switched, and going back is changing `HANDBOOK_RAG_HANDBOOK_COMMIT` back.
2. **Vectors are reused by the text they were made from, not by id.** `handbook-rag index --reuse-from <older commit>` reads the payloads of the older commit's collection first. For every chunk of the newer commit, the dense and the keyword vector are taken from a point of the older collection that was embedded from exactly the same text, and computed only when there is none.
   - **Why the text and not the id.** A chunk below an edit on its page has moved: it has a new id and the same text, and its vectors are still right. A chunk on a page whose title changed keeps its id and has another text: "Expenses > Laptops" became "Spending > Laptops", and its vectors are wrong for it. The same holds for a chunk under a heading renamed to a word of the same length, and for a piece of a long table whose repeated header rows were renamed above it: it covers the same span of the page, and its text is not that span.
   - **How the older collection is read.** Its points hold no record of the embedded text, but their payloads hold everything it is built from: the title, the headings and the chunk's text. So the text is built again from each payload by the same code (`Chunk.text_for_embedding`), and looked up by its SHA-256 hash. New points carry no stored fingerprint either. It would be a second copy of what the payload already holds, which could disagree with it, and it would make every point built after this change differ from the points built before it. What a fingerprint would protect against, a change to how the embedded text is built, is handled instead by a rule written where that text is built: such a change must come with a new chunking version, which gives a new collection whose vectors are never reused.
   - **The match is checked twice.** The older collection is read once, payloads only, before anything is written. Vectors are then fetched a batch at a time, and each fetched point's text is built again and compared before its vectors are used. A point that changed or disappeared in between is embedded instead. Only payloads are held for the whole collection; vectors are held a batch at a time.
   - **Every payload comes from the newer commit's chunk.** A reused point lends its vectors and nothing else. Its address, section, commit and page come from the chunk being stored.
   - **The keyword vector is reused like the dense one.** A chunk's keyword vector depends only on its own text. The rarity of each word across the collection is applied by the store when a question is asked ([ADR 0005](0005-local-embedding-and-reranking-models.md)), so the new collection weights words by its own contents, as a full index would.
3. **The older collection is named by its commit.** Its name follows from that commit with the models and the chunking of the current settings, so a collection made with another embedding model, keyword model or chunking cannot be asked for. When the collection that would fit does not exist, the command refuses, says why (another model's vector for the same text means something else, and another chunking cuts the pages into other texts), and lists the collections that commit does have with what each was made with. It also refuses a commit that is not a full hash, and the collection it is building as its own source. A collection name typed by hand was the other choice; it would have made it possible to name a collection built with other settings, and a check on the name would then have had to stand in for what the commit makes impossible.
4. **The report.** At the end, `index --reuse-from` prints the pages added, changed, removed and unchanged, the chunks whose vectors were reused, the chunks embedded, and how long each part took: chunking the newer commit, reading the older collection, copying reused vectors, and embedding. A page counts as **changed** when what the index holds for it differs: a chunk added, removed or moved, or a chunk's text, title, headings, address, section or token count not the same. The commit each chunk came from is not compared, since it always differs. A page whose file changed only where cleaning removes the text, such as an HTML comment, counts as unchanged, because its index entries are the same. Pages are those that have chunks in the index; a page that became a stub counts as removed. The comparison is made against the older collection, not the older snapshot, so it needs only the collection.
5. **The hole in skipping is closed.** `index` now skips a chunk only when the point stored under its id describes exactly that chunk: same title, headings, address, section, commit, offsets, text and token count. Otherwise the chunk is embedded and stored again, and the summary says how many were replaced. Without the new option the command prints what it printed before; the line about replaced chunks appears only when there are some. It reads every stored payload of the collection, where it read only ids before. A chunk whose address alone changed is embedded again although its vectors are still right; that keeps one rule for skipping, and the case is rare.
6. **How ids are made does not change.** The committed test questions are tied to quotes, but the labelled answers, the adversarial cases and the saved answer runs name passages by chunk id ([labelled answers](../../evals/judge/README.md), [adversarial cases](../../evals/adversarial/README.md), [evaluation guide](../evaluation.md)), and every one of them would break.
7. **This change makes updating possible. It does not update.** The default commit stays `e645aac6dc6fbb0b759b92ed32f016aaed5ef4b8`.

## What "equal to a full index" means

An updated index has to be what a full index of the newer commit would be: the same ids, the same payloads, and vectors that are the same up to the small differences a model gives when it embeds the same text in another batch. Two measures exist for that:

- **On small handbooks made for the tests, exactly.** Two commits hold every case named above, plus a page added, a page removed, an unchanged page, and the same text under the same title on two pages and on a third page that is new. The newer commit is indexed twice, in full and by update, and the two collections are compared with a tolerance of zero: ids, payloads, dense and keyword vectors. The stand-in embedding model used for this gives vectors that the store keeps bit for bit; with another, the store's own rounding (below) would differ in the last bit. The tests also check which texts were embedded, that the older collection is only read, that a point is never reused on its id alone, and that the counts in the report add up.
- **On real pages, within a tolerance.** `handbook-rag check-reuse --reuse-from <older commit>` takes the retrieval gate's slice of the newer commit, the pages that hold the golden set's evidence, and indexes it in memory twice: by embedding every chunk, and by reusing the older commit's vectors for the same pages. It compares the two and prints the largest difference between two dense vectors, the largest between two keyword weights, and the smallest cosine similarity of a pair. Nothing is written to the vector store server. `handbook-rag compare-collections <reference> <candidate>` runs the same comparison on two collections in the store.

**Why a tolerance is needed.** A reused vector was made in another batch than a fresh one would be. A batch is padded to its longest text, and the arithmetic of a different batch can move the last digits of a vector. The store also divides each dense vector by its length when it is stored, and doing that again to a vector that already has length 1 can change its last bit. So an entry of a dense vector may differ by a rounding error, and the comparison allows `1e-4` by default, which `--tolerance` changes. A vector of this model has 384 entries and a length of 1 ([ADR 0005](0005-local-embedding-and-reranking-models.md)), so a typical entry is about 0.05, the square root of 1/384. The default is meant to be far below a difference that could change a search, and above what rounding and batching produce; the real check prints the largest difference it finds, so the margin can be seen. A keyword word present in one vector and missing in the other counts as differing by its whole weight, so the tolerance can never hide a different word.

**Measured on real pages** on 23 November 2026, from the pinned commit to `8fbd57c14d39b64a0bbac86ad8b3d5922797d6f1`, the newest commit of the handbook that day, made two days and 20 hours after the pinned one. The machine was a Mac with the embedding model on its GPU.

| | The slice, by `check-reuse` | The whole handbook |
|---|---|---|
| Pages | 134 of 3,846 | 3,846 |
| Pages added, changed, removed, unchanged | 0, 1, 0, 133 | 2, 7, 2, 3,837 |
| Chunks | 3,278 | 38,891 |

- **The slice** is indexed twice in memory by the command, so both of its indexes pass through the same store.
- **The whole handbook** was compared between two collections on the server. `index --reuse-from` built the newer commit's collection. A full index of the same commit was then built once under another collection name, by a short script that calls the same indexing function on that name, because no command gives a collection another name. The script is not part of the repository. `compare-collections` compared the two. The update was run a second time, and the comparison gave the same result again.
- **The times** are those of the indexing step. Before it, cutting the pages into chunks took 38 to 39 seconds in every run, and reading the older collection's payloads took 3.4 and 2.6 seconds. Of the update's indexing time, 43.1 and 33.6 seconds went into fetching the older vectors and storing them in the new collection, and about 2 seconds into embedding. So an update now waits for the copying, not for the model.
- **The pages that changed** agree with a plain comparison of the two downloaded file trees: 7 files differ, 2 are only in the older and 2 only in the newer.
- **The older collection was only read.** A SHA-256 hash over every id, payload and vector of the pinned collection was the same before and after the second run of the update.
- **The new rule for skipping changed nothing in the pinned collection.** Plain `index` with the new rule skipped all 38,881 chunks in 2.4 seconds, embedded none, removed none, and left the same hash.
- **A difference of 5e-09** is about the last bit of a 32-bit number of the size of a typical entry. The tolerance of `1e-4` is 20,000 times larger.

Not measured: an update on a CPU; an update across a larger change (11 of 3,848 pages differed here, and the cases a larger change brings are covered on the small handbooks of the tests only); and many updates one after another.

## Alternatives considered

- **Update the pinned collection in place.** It would save the space of a second collection, and needs no switch. But during the update the index would be half old and half new, a failed run would leave it that way, and going back would mean another update. The evaluation's saved runs also name the collection they were measured on. A new collection beside the old one makes the switch one setting, in either direction.
- **Compare the two commits' git trees to decide which pages to chunk and embed again.** Git can list the files that changed between two commits. But a list of changed files says which pages to look at, not which chunks to embed: an edit at the top of a long page moves every chunk below it, and those keep their text and their vectors. And a page git does not list can still change in the index, when a setting or the code that reads titles changes. Comparing embedded texts decides chunk by chunk, needs no history between the two commits, and gives what a full run gives by construction. It needs the older collection only, not the older snapshot.
- **Change how ids are made**, so that the id holds the title and headings and skipping by id would be enough. Every chunk id would change, and with them the passages named by the labelled answers and the adversarial cases. It would also not help across commits: a chunk that moved would still get a new id.
- **Switch with a collection alias**, so that the service moves to the new collection without a restart. Qdrant can point an alias at a collection and move it in one step. The service reads its collection's name from the settings when it starts, and a restart is cheap here, so the alias would add a second way of naming the index without a need for it yet. It is the natural next step if the service has to switch while it is running.

## What is still missing before the default commit can move

The pinned commit is what the test questions, the labelled answers, the adversarial cases and the saved runs were made against. Moving it takes more than an index:

1. **The index of the newer commit**, built by this command and checked with `check-reuse`.
2. **The golden set**, [`evals/golden/questions.jsonl`](../../evals/golden/README.md). `make golden-check` must pass on the newer snapshot: every evidence quote word for word in its page and on no other page. A quote whose page changed, moved or now repeats it elsewhere has to be found again, and a question whose answer the handbook changed has to be relabelled or dropped. The set's card says the questions are valid for the pinned commit only, and its checks were made against it.
3. **The labelled answers for the judges**, [`evals/judge/`](../../evals/judge/README.md). The first set names its passages by chunk id with a hash of their text, and loading stops when a passage is gone or reads differently. A passage below an edit on its page has a new id. The passages have to be found again and the labels checked, as the card says for any change of snapshot. The second set and its control are tied to the golden set's reference answers, so they follow any change made there.
4. **The adversarial cases**, [`evals/adversarial/cases.jsonl`](../../evals/adversarial/README.md). They name their passages by chunk id and hash too, and a case whose passage reads otherwise stops the run before a request is spent.
5. **The saved runs**, [`evals/runs/`](../../evals/runs). Each records the commit and the collection it was measured on. Runs made on two commits are not comparable question by question, so the baselines have to be made again: retrieval locally, and the answers, the two judges and the adversarial cases with real requests, within the free key's daily allowance.
6. **The retrieval gate**, [`evals/gate.json`](../../evals/gate.json). Its slice follows the golden set, and its minimums were measured at the pinned commit, so it has to be measured again. CI keeps its snapshot under a key that holds the commit, so it downloads the newer one once.
7. **The README's results**, which a test holds to the committed runs, and the licence statement in ADR 0002, which was checked at the pinned commit and has to be checked again at the newer one.
8. **Then the default itself**, in `config.py` and `.env.example`, with the older collection kept for going back.

## Consequences

- Updating the index to a newer commit embeds only the chunks whose embedded text is new. On the whole handbook, for a commit nearly three days newer, that was 44 of 38,891 chunks, and an indexing step of 38 to 47 seconds where a full index took 394 on the same machine.
- `index` reads every stored payload of its collection before it decides what to skip, where it read ids only. Without the new option it prints what it did before, unless it finds chunks stored with other details, which it now replaces.
- `snapshot` refuses to replace a snapshot of another commit in place, unless it is given `--replace`. Downloading a newer commit is meant to happen in a second data directory, and forgetting to set it would otherwise replace the pinned snapshot that the test questions are checked against.
- A change to how the embedded text is built (the title and the headings before the chunk) must come with a new chunking version. The rule is written in `Chunk.text_for_embedding`. Without it, both an update and plain indexing would take vectors of the old form for the new one.
- Each time a vector is reused, the store rounds it again when it stores it. Over many updates the rounding errors could add up; each is around the last bit of a 32-bit number, far below the tolerance.
- The comparison of two whole collections reads both point by point, a batch at a time. A comparison of an updated index with a full index of the whole handbook needs a second full index under another collection name, which no command builds. For the measurement above it was built once by a script, and comparing the two collections of 38,891 points took 32 seconds. The slice is the check on real pages that a command repeats.
