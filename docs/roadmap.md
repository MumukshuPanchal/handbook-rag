# Roadmap

Work is grouped into milestones. Each milestone ends with something that runs and, from M2 onwards, with numbers that can be compared against the milestone before it. Individual tasks are tracked as GitHub issues under the matching milestone.

## Milestones

The last column is the final state of each milestone for version 1.0.0, released on 23 November 2026. Where a milestone is not fully done, it says what is missing.

| Milestone | Outcome | Done when | State on 23 November 2026, at version 1.0.0 |
|---|---|---|---|
| **M0 Foundations** | A repository others can build on | Charter, architecture and decision records are reviewed. Lint, tests and CI pass on the project skeleton. | Done |
| **M1 Baseline pipeline** | A question gets a cited answer end to end, using the simplest approach that works | The handbook snapshot is indexed by a repeatable command. `ask` returns an answer with citations, or abstains. | Done: `ask` answers real questions with citations, or declines, using Gemini (ADR 0013). The Claude generator is written and has not been run against its API |
| **M2 Evaluation** | Quality has numbers | The golden set is reviewed and signed off. Baseline retrieval and answer metrics are recorded. CI fails when retrieval quality drops. | Done except a person's check. Retrieval metrics and the CI gate are done. Answers: the scores that code can compute, and the two judged scores, "supported by its sources" and "correct by the reference", are recorded for all 165 questions, each judge checked against labelled answers first (ADR 0014). Not done: no person has checked the golden set or the labels the judges were checked against. Both were made and checked by model sessions, so the golden set is not signed off. A person's check of a sample is what remains of [issue 8](https://github.com/MumukshuPanchal/handbook-rag/issues/8) |
| **M3 Retrieval quality** | Better retrieval, shown by the numbers | Hybrid search and reranking are each compared with the baseline. Chunking and embedding experiments are recorded. Defaults are chosen from the results. | Done for search, fusion and chunk size: hybrid is the default (ADR 0011). No other embedding model has been tried ([issue 12](https://github.com/MumukshuPanchal/handbook-rag/issues/12)) |
| **M4 Observability** | Every request can be explained | Each request produces a trace with per-stage timing, retrieved chunks, and token usage, viewable in a local trace UI. | Done: a search and an answer each leave one trace, the model call included, with its token usage under the names of OpenTelemetry's conventions for generative AI (ADR 0008). A real streamed answer on 23 November 2026 left 13 spans, with the model call taking 1,671 of 1,788 ms and reporting 1,767 tokens read and 133 written ([the guide](observability.md#the-trace-of-an-answer)). A backend built for language-model applications has not been tried |
| **M5 Serving** | Usable as a service | An HTTP API with streaming answers. `docker compose up` starts the whole system. | Done: `POST /ask` answers as one JSON response or as server-sent events (ADR 0015), next to `POST /search`, and `docker compose up` passes the Gemini key from `.env`. `POST /ask` answered real questions on 23 November 2026, run on the host and in the Compose container. Not built for the open internet: no authentication and no rate limit for each caller. Since [ADR 0018](adr/0018-time-limits-retries-and-a-fallback.md) a model call has time limits, repeats that are counted and traced, and an optional fallback model, tried on an overloaded evening; a fallback that succeeds has not been seen yet |
| **M6 Hardening and release** | Ready to show | Tests cover prompt injection and unanswerable questions. Claude tiers are compared on quality, latency and cost. The README reports results and limitations. `v1.0.0` is tagged. | Done except the comparison of Claude tiers. The adversarial tests are done: 36 cases plant instructions in passages and ask questions outside the handbook, run against the real answer model, with the replies code cannot decide read by two model sessions ([the guide](evaluation.md#adversarial-tests)). On 23 November 2026, 12 of 20 planted instructions were not followed and 15 of 16 out-of-scope questions were declined. What got through is documented and not fixed ([issue 66](https://github.com/MumukshuPanchal/handbook-rag/issues/66)). Not done: the comparison of Claude tiers ([issue 17](https://github.com/MumukshuPanchal/handbook-rag/issues/17)), because it needs a paid key; the answer model was chosen among free models by the measurements in ADR 0013. A test that the assistant corrects a false assumption instead of going along with it is filed under this milestone and not done either ([issue 37](https://github.com/MumukshuPanchal/handbook-rag/issues/37)). The [README](../README.md) reports the results and the limitations, and a test holds its numbers to the committed runs. `v1.0.0` is tagged with this release |

## Why this order

- **Baseline before improvements.** The simplest pipeline comes first so there is something to measure.
- **Evaluation before optimisation.** M2 comes before M3 because an improvement that cannot be measured cannot be claimed.
- **Tracing before serving.** Traces make the API easier to debug while it is being built.

## After 1.0

The open issues, in the order they should be taken up. First what decides how far the numbers can be trusted, then the failures the evaluation found, then the service, then everything else. Each issue says what done means.

1. **A person checks a sample of the golden set and of the labels** ([issue 8](https://github.com/MumukshuPanchal/handbook-rag/issues/8)). Every score rests on questions and labels that only model sessions have checked. It costs no requests, only reading time.
2. **Harden the assistant against planted instructions, then measure again** ([issue 66](https://github.com/MumukshuPanchal/handbook-rag/issues/66)). It is the one known failure with a security cost: a page can add a link to answers or silence the assistant about itself. A boundary that passages cannot forge ([issue 52](https://github.com/MumukshuPanchal/handbook-rag/issues/52)) is part of it. New instructions mean running the answer evaluation again, which takes about 460 requests: nearly a whole day of the free allowance, and more when attempts have to be repeated. The same change can give the model a fixed form for "this part is not in the handbook". The answer cache would then know a decline in part exactly, where it now goes by a list of phrases ([what is still missing](adr/0020-an-answer-cache-that-matches-by-meaning.md#what-is-still-missing)).
3. **Measure how often the answers leave out a limit or an exception, then reduce it** ([issue 59](https://github.com/MumukshuPanchal/handbook-rag/issues/59)). A judge that sees the fault is kept now, below. The 129 saved answers hold too few cases to show a change, so the first step is to ask the questions of the 40 limit answers for real and judge the answers with version 2 of the judge. Reducing it means new instructions, which come with item 2, and the answers measured again. Version 2 is told the two rules that version 1 lacks; the slip in the numbering of version 1 ([issue 58](https://github.com/MumukshuPanchal/handbook-rag/issues/58)) is not measured for it.
4. **Compare Claude tiers** ([issue 17](https://github.com/MumukshuPanchal/handbook-rag/issues/17)). It needs a paid key. It would also give a judge of another model family, which ADR 0014 names as the better design, and the first cost per answer in money.
5. **Grow the questions written without the passage** ([issue 43](https://github.com/MumukshuPanchal/handbook-rag/issues/43)), so that the choice between hybrid and keyword search can be settled (ADR 0011). Test questions with a false assumption at the same time ([issue 37](https://github.com/MumukshuPanchal/handbook-rag/issues/37)).
6. **Keep each reply as the model wrote it** ([issue 60](https://github.com/MumukshuPanchal/handbook-rag/issues/60)), so that a change to the citation parser can be tested on every real reply collected.
7. **Retrieval experiments**: repeated text in the corpus ([issue 34](https://github.com/MumukshuPanchal/handbook-rag/issues/34)), other embedding models ([issue 12](https://github.com/MumukshuPanchal/handbook-rag/issues/12)), and how many candidates each search gives the merge ([issue 51](https://github.com/MumukshuPanchal/handbook-rag/issues/51)). Search already finds the passage for 0.962 of the questions ([the run](../evals/runs/retrieval/v2)), so these come after the failures above.
8. **Speed and convenience**: a faster retrieval gate ([issue 47](https://github.com/MumukshuPanchal/handbook-rag/issues/47)), and showing in the terminal which sentence rests on which source ([issue 61](https://github.com/MumukshuPanchal/handbook-rag/issues/61)).
9. **Stretch goals**: query rewriting before retrieval ([issue 22](https://github.com/MumukshuPanchal/handbook-rag/issues/22)).

Done since 1.0:

- **A demo web page** ([issue 19](https://github.com/MumukshuPanchal/handbook-rag/issues/19)): the API serves a page at `/` where a question's answer can be watched as the model writes it, with its sources and what the search found ([ADR 0016](adr/0016-a-demo-page-without-a-build-step.md)).
- **An MCP server** ([issue 20](https://github.com/MumukshuPanchal/handbook-rag/issues/20)): `handbook-rag mcp` offers the handbook search as a tool ([ADR 0017](adr/0017-an-mcp-server-for-search.md)).
- **Time limits, repeats and a fallback for model calls** ([issue 42](https://github.com/MumukshuPanchal/handbook-rag/issues/42)): one request may be silent for 20 seconds, the model may be tried again for 30, every request is counted and traced, and a second model can stand in when the first gives up ([ADR 0018](adr/0018-time-limits-retries-and-a-fallback.md)). Tried on an overloaded evening: a silent model was given up after two requests and 42 seconds, and a fallback that was asked failed too. A fallback that succeeds has not been seen yet.
- **Updating the index to a newer commit** ([issue 21](https://github.com/MumukshuPanchal/handbook-rag/issues/21)): `index --reuse-from` indexes a newer commit into a collection of its own and embeds only the chunks whose embedded text changed, taking the other vectors from the pinned commit's collection, which is only read. On small handbooks made for the tests the result equals a full index exactly. On the real handbook, for a commit nearly three days newer, it embedded 44 of 38,891 chunks, its indexing step took 38 and 47 seconds in two runs, each into an empty collection, against 394 for a full index, and the result matched the full index on every id and payload, with the dense vectors of one chunk at most 5e-09 apart and all others identical ([ADR 0019](adr/0019-updating-the-index-by-reusing-vectors.md)). The default commit has not moved: the test questions, the labelled answers and the saved runs are tied to it, and the decision record lists what moving it takes.
- **A semantic cache** ([issue 24](https://github.com/MumukshuPanchal/handbook-rag/issues/24)) was measured before it was built. On 198 pairs of a test question and a rewording or a near-miss, the similarity of two embeddings alone could serve nothing safely. A second model that reads the two questions together served 7 of 49 rewordings and none of 50 near-misses on the half of the pairs that chose nothing. That half held no near-miss hard enough to test the threshold: on 200 other splits of the pairs, the same rules served something wrong in the 97 that put the hardest near-miss there ([the guide](evaluation.md#a-semantic-cache-measured-before-it-is-built)). No person has read the pairs.
- **The answer cache** ([issue 24](https://github.com/MumukshuPanchal/handbook-rag/issues/24)) is built, and on by default in the mode that also matches by meaning, as the owner of the project decided ([ADR 0020](adr/0020-an-answer-cache-that-matches-by-meaning.md)). The same question is served its stored answer without a request to the model, a decline too. A question worded differently is served a stored answer when the second model's weaker direction reaches 0.91. That threshold is fitted on the labelled pairs, with the simulated cache filled with the replies of the saved answer run and the cache's own code deciding which of them may be served by meaning. On the half of the pairs that chose nothing it served 16 of 49 rewordings and nothing wrong. That half again held nothing hard near the threshold: on 200 other splits of the pairs the rule's own threshold, 0.8669, served something wrong in 73 ([the guide](evaluation.md#the-answer-cache-measured-as-it-is-built)). It was checked with the real service twice: with 7 requests before its last changes, and with 2 after them. A question that only looks like a stored one will sometimes be served its answer. A cached answer names the question it was written for, and nothing is measured on real questions.

Started since 1.0, and not finished:

- **Questions that need two passages** ([issue 78](https://github.com/MumukshuPanchal/handbook-rag/issues/78)) are measured, and the search is not changed. Almost every test question rests on one passage, so 34 questions whose answer needs two passages on two pages were written, and a second reading confirmed 33, both by model sessions. The default search gives the model both passages for 12 of the 33, and at least one for 26. Fourteen changes to the search that need no request to a model were tried, and none was adopted: none finds both passages clearly more often, and a limit on the chunks of one page takes the passage from questions that rest on one ([ADR 0021](adr/0021-two-passage-questions-and-the-search-as-it-is.md), [the guide](evaluation.md#questions-that-need-two-passages)). For 16 of the 33 a passage is not among the first ten results at all. What remains is a request to a model before the search, to split a question that asks for two things, which belongs with the request for follow-up questions ([issue 79](https://github.com/MumukshuPanchal/handbook-rag/issues/79)), and answers on these questions: none has been written, and no person has read the questions.
- **Follow-up questions** ([issue 79](https://github.com/MumukshuPanchal/handbook-rag/issues/79)) have a step that rewrites them into a question that stands alone, built and measured, and not wired in. 82 labelled conversations were written by one model session and read again by two more. On one run with the real model, 35 of 43 follow-ups got a question that means an acceptable form, 16 of 17 questions that stand alone were left alone, and none of the 22 planted instructions was followed. The step is given the questions only, and of the 8 follow-ups that point into an answer it got 2 right ([ADR 0022](adr/0022-follow-up-questions-rewritten-before-the-search.md), [the guide](evaluation.md#follow-up-questions)). What remains is the wiring: `POST /ask` and the demo page with the earlier turns, and the answer cache on the rewritten question. No answer was written for the rewritten questions, and no person has read the cases.
- **Answers that leave out a limit** ([issue 59](https://github.com/MumukshuPanchal/handbook-rag/issues/59)) can be measured, and are not reduced. 120 answers on 40 passages were written to test the fault, and labelled twice, by model sessions. Version 1 of the judge, which gives every published score, caught 13 of the 39 limits left out. Version 2, written for the fault, caught 33, with one false alarm in 157 statements, and it sends no more requests ([ADR 0023](adr/0023-a-second-version-of-the-support-judge-for-dropped-limits.md), [the guide](evaluation.md#limits-that-an-answer-leaves-out)). On the first labelled answers it is worse than version 1, with 2 false alarms on real answers where version 1 raised 1, and it calls 125 of the 129 answers of the `baseline` run supported where version 1 calls 127. So version 1 stays the judge of every published score, and version 2 is kept beside it for this one fault. Answers that keep their limits come with item 2.

## How work flows

1. Every task starts as an issue with a "done when" checklist.
2. Work happens on a short-lived branch named `type/short-description`.
3. A pull request links the issue, passes CI, and includes tests and documentation for what it changes.
4. Pull requests are merged by fast-forward, so `main` keeps a linear history in which every commit is a meaningful step.
5. A decision that changes the design gets a decision record in the same pull request.
